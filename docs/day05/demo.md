这个项目目前是一个只读的教学股票研究 Agent。它的重点不是预测股票或者自动交易，而是验证一个 Agent 从模型决策、工具调用、结果回传，到最终结构化回答的完整闭环，以及整个过程中安全边界是否可靠。

目前工具返回的仍然是本地 fixture 教学数据，并不是真实行情，也不会执行任何交易操作。

我先演示一个正常路径，也就是 D05-02。

用户的问题是：“查询 NVDA 教学模拟报价。”

Agent 收到问题后，不直接编造价格，而是把当前消息、可用工具定义以及输出格式要求发送给模型。

模型判断需要查询报价，因此返回一个 `get_quote` 的 tool call。

这个 tool call 不会被直接执行。程序首先经过工具调用层检查，包括 `tool_call_id` 是否有效、工具是否在白名单里，以及参数能否通过 Pydantic 校验。

只有这些检查全部通过后，Python handler 才会真正执行。

`get_quote` 返回的是本地 fixture，例如 NVDA 的模拟报价 100 USD，同时注明这是教学模拟数据，不是真实行情。

Agent 会为这份工具结果生成 evidence ID，比如 E1，然后使用原来的 `tool_call_id` 把工具结果回传给模型。

模型拿到工具结果以后，再生成最终的 `ResearchOutput`。最终回答除了要符合 JSON Schema，还必须通过 evidence 校验，也就是说模型在 facts 和 inferences 中引用的证据 ID 必须确实来自本次输入或者本次成功的工具调用。

这一整条链路我除了做离线测试以外，也已经使用 DeepSeek 的真实模型 API 跑通过。真实模型完成了 tool call、Python handler 执行、tool result 回传，以及第二轮结构化回答，最终状态是 `completed`，自动检查也是 `pass`。

这里还有一个比较有意思的现象：真实模型除了 `get_quote`，还额外调用了 `get_company_profile`。这个调用是合法的，也没有超过预算，所以不会导致验收失败，但它属于一个可以继续优化的 unnecessary tool call。后续可以通过 prompt 或 planning 策略，让模型只调用回答问题真正需要的工具。

接下来我演示一个失败路径，也就是 D05-07。

这个案例中，模型固定请求了一个叫 `delete_file` 的工具。

但是这个工具根本不在我的白名单里。

所以即使模型要求执行它，Python 层也不会相信模型。系统会返回 `unknown_tool`，对应 handler 的实际执行次数是 0。

然后模型拿到这个工具错误以后，只能承认自己没有取得报价，而不能伪造一个查询成功的结果。

这个案例体现了我为什么不能只在 system prompt 里写一句“不要调用危险工具”。

Prompt 本质上只是对模型的软约束，模型可能理解错误、输出错误，也可能因为模型升级或者不同 provider 的行为差异而发生变化。

真正的安全边界必须放在程序层。

所以这里我做了几层约束：工具白名单、Pydantic 参数校验、tool call ID 校验、工具调用次数预算、模型轮数预算、单工具超时以及整个任务的总超时。

例如模型如果不断请求工具，不应该让 Agent 无限循环或者一直消耗 API token。我在 D05-10 中专门测试了这个情况，当模型达到最大轮数以后，系统会以 `budget_exhausted` 结束，而不会继续执行。

最后是验证体系。

这一周我没有只写几个 happy path 然后认为 Agent 已经可靠，而是做了 10 个固定案例，包括正常报价、公司资料、缺失信息、证据冲突、非法参数、未知工具、工具超时、非法 evidence ID 和循环调用。

离线案例是 10/10 自动符合预期，全量 pytest 是 91 个通过。

但自动测试并不能证明模型说的每句话都真的被证据支持。

比如模型完全可以引用 E1，但是把 E1 中的 100 USD 写成 120 USD。对于程序来说，E1 是合法 evidence ID，但语义其实已经错了。

因此我又增加了人工事实复核。

人工检查数字、单位、报告期、数据模式、证据冲突，以及模型有没有把 fixture 描述成真实行情。目前 10 个案例都已经完成人工复核。

所以这套验证实际上分成两层：

第一层是程序自动验证，保证结构、安全边界和协议正确。

第二层是人工事实复核，保证回答中的事实真的受到证据支持。

我认为这也是 Agent 系统和普通 API 调用最大的区别之一：模型输出本身是不完全可信的，所以模型负责决策和生成，而真正的权限、安全和结果验证必须由确定性的程序逻辑来兜底。
